# Análise Técnica de Viabilidade — Pipeline RAG | NovaTech

---

## 1. Análise por Tipo de Fonte

### 1.1 PDFs com Tabelas Complexas (SharePoint)

**Desafio:** Tabelas com 15+ colunas raramente sobrevivem ao parsing padrão via PyPDF2 ou PDFMiner. A extração linha-a-linha destrói a relação entre cabeçalho e célula, transformando dados estruturados em texto degenerado. Fluxogramas embutidos como imagem são completamente ignorados por parsers de texto.

**Impacto na qualidade:** O LLM recebe fragmentos como `"Aprovado | João | 2024-01 | 87% | ..."` sem saber o que cada coluna representa, gerando respostas numericamente corretas mas semanticamente erradas. Fluxogramas (geralmente mapeiam processos críticos) ficam invisíveis ao sistema.

**Estratégia de tratamento:**
- Usar **Unstructured.io** ou **Azure Document Intelligence** para extração estruturada de tabelas em HTML/Markdown
- Serializar tabelas como Markdown antes do chunking: o LLM compreende `| Coluna A | Coluna B |` muito melhor que texto plano
- Para fluxogramas: aplicar um modelo multimodal (GPT-4o Vision ou Claude 3.5 Sonnet) para gerar descrição textual das imagens durante o pré-processamento
- Tratar cada tabela como uma unidade de chunk independente, mesmo que ultrapasse o tamanho padrão

---

### 1.2 PDFs Escaneados (OCR necessário)

**Desafio:** PDFs escaneados são essencialmente imagens. Sem OCR, o conteúdo é zero para o pipeline. Com OCR de baixa qualidade, erros ortográficos sistêmicos (ex: `"saldo" → "saIdo"`) degradam os embeddings, pois o vetor semântico do token correto e do token com erro OCR divergem no espaço vetorial.

**Impacto na qualidade:** Baixa similaridade coseno entre a query e chunks OCR-degradados causa falha de retrieval — o documento existe na base mas nunca é recuperado. Isso é um falso negativo silencioso, o pior tipo de falha em RAG.

**Estratégia de tratamento:**
- Usar **Tesseract 5+ com LSTM** ou, para maior precisão, **AWS Textract / Google Document AI**
- Aplicar pós-processamento com spell-checker em domínio (dicionário corporativo customizado) para corrigir erros recorrentes de OCR
- Gerar score de confiança OCR por página; páginas abaixo de 85% de confiança devem ser sinalizadas para revisão humana antes de ingestão
- Considerar re-embedding periódico após correções de OCR

---

### 1.3 Wiki Confluence com Links Internos e Macros

**Desafio:** Links internos (`[Ver Política X](page:12345)`) perdem o destino após extração de texto — ficam como referências mortas. Macros customizadas (ex: `{jira-issues}`, `{status}`) são renderizadas dinamicamente pelo Confluence mas aparecem como tags literais no HTML exportado, sem conteúdo.

**Impacto na qualidade:** Chunks que deveriam carregar contexto completo ficam truncados ou com referências inúteis. Um chunk pode dizer "conforme descrito em [Política de Aprovação]" sem que o sistema saiba o que essa política diz, forçando o LLM a alucinar o conteúdo referenciado.

**Estratégia de tratamento:**
- Usar a **API REST do Confluence** (não exportação HTML) para acessar o conteúdo renderizado das macros
- Implementar **graph-aware chunking**: ao detectar um link interno, injetar um resumo da página destino (máximo 200 tokens) como contexto adjacente ao chunk
- Mapear o grafo de dependências entre páginas para identificar "hubs" (páginas muito linkadas) e priorizá-las no retrieval
- Strips de macros não-renderizáveis devem ser removidos do texto final antes do embedding

---

### 1.4 Planilhas Excel com Fórmulas Interdependentes

**Desafio:** Fórmulas como `=SE(B3>VLOOKUP(A3,Tabela!$A:$C,3,0), "Aprovado", "Reprovado")` são completamente opacas para embeddings — o vetor representa a string da fórmula, não o resultado nem a lógica de negócio. Além disso, planilhas têm estrutura tabular 2D que se perde na serialização linear.

**Impacto na qualidade:** Perguntas do tipo "qual é o critério de aprovação para X?" não encontrarão resposta, pois a regra existe como lógica de fórmula, não como texto. O sistema pode retornar `"=SE(B3>..."` como resposta, que é inútil para o usuário final.

**Estratégia de tratamento:**
- **Executar as planilhas via openpyxl** com `data_only=True` para capturar valores calculados, não as fórmulas
- Para fórmulas com lógica de negócio complexa, usar um LLM para gerar descrição em linguagem natural da regra (ex: "A aprovação ocorre quando o valor em B excede o limite da tabela de referência para aquele item") — indexar essa descrição, não a fórmula
- Serializar abas como Markdown tabulado; manter metadados do nome da aba e do arquivo como prefixo de cada chunk
- Tratar cada aba como unidade de documento independente

## 3. Análise de Orçamento de Contexto

### Configuração do GPT-4o

| Item                          | Tokens     |
|-------------------------------|-----------|
| Janela total                  | 128.000   |
| System prompt                 | ~2.000    |
| Query do usuário              | ~500      |
| Espaço para resposta gerada   | ~2.000    |
| **Disponível para chunks**    | **~123.500** |

### Capacidade de Chunks por Query

```
123.500 tokens disponíveis ÷ 500 tokens por chunk = ~247 chunks máximos
```

### O que isso significa na prática

**247 chunks de 500 tokens cobrem apenas ~3% da base total** (123.500 / 4.133.000). O retrieval precisa selecionar o 3% certo — a qualidade do embedding e da query são determinantes absolutos.

**Impacto no chunking:**
- Chunks muito pequenos (< 200 tokens): perdem contexto local, a informação fica incompleta
- Chunks muito grandes (> 800 tokens): desperdiçam orçamento de contexto; cada chunk "caro" desloca outros potencialmente relevantes
- **500 tokens é o ponto de equilíbrio** — carrega contexto suficiente e permite ~10-20 chunks altamente relevantes por query (uso real vs. teórico)

**Impacto no retrieval:**
- Na prática, recuperar 5 a 15 chunks por query é o padrão — não os 247 teóricos
- Com chunks menores (~300 tokens), é possível recuperar mais candidatos sem saturar o contexto
- Reranking (cross-encoder) antes de enviar ao LLM é essencial para filtrar falsos positivos do retrieval inicial

## 4. Estratégia de Chunking Recomendada

### Fundamento: tipos de pergunta × efeito lost in the middle

O efeito "lost in the middle" demonstra empiricamente que LLMs têm performance degradada para informações posicionadas no meio de contextos longos. As informações no início e no final do contexto são privilegiadas.

### Estratégia Recomendada: Chunking Híbrido com Posicionamento Estratégico

#### 4.1 Por tipo de conteúdo

| Tipo de conteúdo     | Tamanho de chunk | Justificativa |
|----------------------|-----------------|---------------|
| Texto narrativo (wiki, PDF) | 400–500 tokens com overlap de 50 tokens | Preserva coerência semântica sem desperdiçar contexto |
| Tabelas              | 1 tabela = 1 chunk (tamanho variável) | Tabela fragmentada é ininterpretável |
| Planilhas            | 1 aba = 1 chunk + metadados | Contexto da aba é necessário para interpretar valores |
| Fluxogramas          | 1 descrição gerada = 1 chunk | Gerada no pré-processamento por modelo multimodal |

#### 4.2 Por tipo de pergunta do usuário

**Perguntas factuais pontuais** (ex: "Qual é o prazo para X?"): chunks menores (~300 tokens), retrieval top-3. A resposta está em um único ponto — trazer muitos chunks polui o contexto.

**Perguntas de processo/procedimento** (ex: "Como faço Y passo a passo?"): chunks maiores (500 tokens) com overlap, retrieval top-5 a top-8. O processo pode estar fragmentado em múltiplos chunks sequenciais — overlap de 50 tokens evita quebra de sequência.

**Perguntas analíticas/comparativas** (ex: "Compare as políticas de A e B"): retrieval top-10 a top-15 com reranking por cross-encoder. Aqui o risco de lost in the middle é maior — **os chunks mais relevantes devem ser posicionados no início e fim do contexto injetado**, não no meio.

#### 4.3 Mitigação do efeito lost in the middle

1. **Reordenação por relevância na injeção**: após retrieval e reranking, posicionar o chunk de maior score no início do contexto, o segundo maior no final, e os demais no meio — o LLM vai "lembrar" melhor os extremos
2. **Limite conservador de chunks por query**: preferir 8-12 chunks de alta qualidade a 20-30 chunks mediocres — menos competição por atenção
3. **Metadados como prefixo**: iniciar cada chunk com `[Fonte: NomePDF | Página: X | Seção: Y]` — o LLM usa esses sinais para atribuir credibilidade e o usuário pode auditar a resposta

#### 4.4 Implementação recomendada

```
Pipeline de Ingestão:
  1. Extração por tipo (Unstructured.io / Confluence API / openpyxl)
  2. Limpeza e normalização (OCR correction, macro stripping)
  3. Chunking semântico (sentence-transformers para detectar quebras naturais)
  4. Geração de embeddings (text-embedding-3-large ou equivalente)
  5. Indexação no vector store (PGVector ou Pinecone)

Pipeline de Query:
  1. Embedding da query
  2. Retrieval top-20 (ANN search)
  3. Reranking cross-encoder → seleciona top-10
  4. Reordenação anti-lost-in-the-middle
  5. Montagem do prompt com metadados
  6. Geração com GPT-4o
```

---

### Resumo Executivo

A base da NovaTech tem ~4,1M tokens — **RAG com retrieval seletivo é a única abordagem viável**. Os maiores riscos de qualidade são: (1) tabelas e fluxogramas mal extraídos, (2) OCR degradado em PDFs escaneados, e (3) perda de referências cruzadas na wiki. Com chunking híbrido de 400–500 tokens, reranking e posicionamento estratégico anti-lost-in-the-middle, é possível atingir qualidade de resposta alta para perguntas factuais e de processo. Perguntas analíticas complexas exigem retrieval mais sofisticado e são o principal ponto de atenção para iteração futura.

## Crítica à Análise da Parte 1

### Pontos fracos ou superficiais

**1. OCR sem base para o threshold de 85%**
O threshold de confiança de 85% aparece sem justificativa. Esse número varia radicalmente por ferramenta (Tesseract vs. Textract têm escalas diferentes), tipo de fonte (fonte serifada vs. manuscrito) e consequência de erro (documento jurídico vs. FAQ interno). Um threshold único é ingênuo — o correto é estratificado por criticidade de documento.

**2. Graph-aware chunking sem implementação real**
"Injetar um resumo da página destino (máximo 200 tokens) como contexto adjacente" soa bem, mas não endereça: como detectar se o link destino também tem links? Como evitar expansão recursiva do grafo? Como lidar com links circulares? A estratégia está incompleta.

**3. openpyxl com `data_only=True` tem uma limitação crítica não mencionada**
`data_only=True` só retorna valores calculados se o arquivo Excel foi **salvo após o último cálculo em Excel**. Arquivos gerados programaticamente ou nunca abertos no Excel retornam `None` para todas as células com fórmula. Isso é um bug silencioso que destrói a estratégia inteira para planilhas geradas por sistema.

**4. Busca puramente semântica (um risco grave omitido)**
A análise inteira assume busca por similaridade de embedding. Busca semântica falha em: termos exatos de negócio ("NF-e 3.10", "Cláusula 4.2.1", códigos de produto), abreviações corporativas e siglas. Não há menção a **busca híbrida (BM25 + dense embeddings)**, que é o padrão da indústria exatamente por cobrir esse gap.

**5. Nenhuma estratégia de avaliação**
A análise entrega um pipeline, mas não diz como saber se ele funciona. Sem métricas como **faithfulness, context recall e answer relevancy** (framework RAGAS), não é possível comparar estratégias de chunking nem detectar regressões após atualizações da base.

**6. Ausência de fallback quando o retrieval falha**
Quando nenhum chunk relevante é recuperado, o LLM ainda gera uma resposta — potencialmente alucinando com alta confiança. Esse é o cenário mais perigoso em RAG corporativo e não foi endereçado.

---

### Estimativas otimistas demais

**Token count subestimado para tabelas em Markdown**
300 palavras/página foi usado como base para PDFs com tabelas de 15+ colunas. Uma tabela com 15 colunas e 20 linhas serializada em Markdown tem ~800 tokens apenas para a estrutura — o cabeçalho repetido em cada linha e os separadores `|` inflam drasticamente o count. O estimate de 3,2M tokens para PDFs provavelmente é 30–50% baixo para esse corpus específico.

**Metadados de chunk não contabilizados**
A recomendação de prefixar cada chunk com `[Fonte: NomePDF | Página: X | Seção: Y]` adiciona ~20 tokens por chunk. Com ~8.000 chunks estimados na base, isso é +160.000 tokens de overhead na ingestão — irrelevante na base, mas relevante no orçamento de contexto por query (cada chunk consumido custa 20 tokens extras).

**2.000 tokens para resposta gerada é insuficiente**
Para perguntas analíticas ("Compare as políticas de A e B com base nos documentos"), respostas estruturadas facilmente ultrapassam 2.000 tokens. O orçamento de contexto deve reservar pelo menos 4.000 tokens para resposta, reduzindo os chunks disponíveis de ~247 para ~242 — impacto pequeno, mas a subestimação revela que o modelo mental de uso foi o de perguntas simples.

---

### Riscos não considerados

**Controle de acesso e segurança**
Documentos no SharePoint têm permissões por usuário/grupo. Um pipeline RAG que indexa tudo indiscriminadamente pode expor conteúdo restrito a usuários sem permissão. Isso é um risco de compliance, não apenas técnico.

**Atualização e versionamento da base**
Quando um PDF é atualizado no SharePoint, o que acontece com os chunks antigos no vector store? A análise não menciona estratégia de re-ingestão incremental, detecção de documentos modificados ou invalidação de embeddings stale. Em bases corporativas vivas, isso é crítico.

**Drift semântico entre embedding e geração**
Se o modelo de embedding for atualizado (ex: migração de `text-embedding-ada-002` para `text-embedding-3-large`), todos os embeddings existentes ficam incompatíveis com as queries novas. Um re-embedding completo da base custa tempo e dinheiro — e não há plano para isso.

**Custo operacional ausente**
Não há estimativa de custo. Azure Document Intelligence cobra por página, OpenAI cobra por token de embedding e geração. Para 800 PDFs × 10 páginas, o custo de processamento inicial com Document Intelligence pode ser significativo, e o custo de embedding de 4,1M tokens precisa ser quantificado antes de qualquer decisão de arquitetura.

- **API REST do Confluence** (endpoint `/wiki/rest/api/content/{id}?expand=body.storage`) para conteúdo renderizado, nunca exportação HTML

- Mapear o grafo de dependências; páginas com grau de entrada alto (hubs) recebem boost de relevância no retrieval
- Macros não-renderizáveis: remover tags e adicionar metadado `[macro_removida: jira-issues]` para auditoria
- **Ciclos no grafo**: detectar e quebrar antes da ingestão (registro em log para revisão editorial)

**Impacto na qualidade:** Perguntas sobre critérios e regras de negócio não encontram resposta; o sistema pode retornar `"=SE(B3>..."` como resposta, que é inútil.

**Estratégia de tratamento:**
- **Pipeline de dois estágios**: (1) tentar `data_only=True`; se células críticas retornarem `None`, (2) abrir o arquivo via COM automation (Windows) ou LibreOffice headless para forçar recálculo antes da extração
- Para fórmulas com lógica de negócio: usar LLM para gerar descrição em linguagem natural da regra — indexar a descrição, não a fórmula
- Serializar cada aba como Markdown tabulado com prefixo de metadados `[Arquivo: X | Aba: Y]`
- Tratar cada aba como documento independente; manter mapa de dependências entre abas como metadado

### Implicações práticas

**Cobertura**: 15 chunks × 500 tokens = 7.500 tokens de contexto por query → cobre 0,16% da base. O retrieval precisa acertar o 0,16% certo. Isso torna a qualidade do embedding e a estratégia de query expansion determinantes absolutos, não opcionais.

**Busca híbrida é obrigatória**: busca semântica pura falha em termos exatos ("Cláusula 4.2.1", "Código 8721-B"). A combinação BM25 (keyword) + dense embedding com fusão por **Reciprocal Rank Fusion (RRF)** cobre ambos os casos sem custo adicional de infraestrutura significativo.

**Fallback obrigatório**: quando nenhum chunk ultrapassa threshold mínimo de relevância (cosine similarity < 0.70), o sistema deve responder "Não encontrei informação suficiente para responder com segurança" em vez de gerar resposta com contexto irrelevante.

## 4. Estratégia de Chunking Recomendada

### Estratégia: Chunking Híbrido com Busca Híbrida e Avaliação Contínua

#### 4.1 Por tipo de conteúdo

| Tipo de conteúdo | Tamanho de chunk | Overlap | Justificativa |
|------------------|-----------------|---------|---------------|
| Texto narrativo (wiki, PDF) | 400–500 tokens | 75 tokens | Overlap maior (vs. 50 da v1) reduz quebras em boundaries de frase em português |
| Tabelas | 1 tabela = 1 chunk atômico | — | Tabela fragmentada é semanticamente inútil |
| Planilhas | 1 aba = 1 chunk + metadados | — | Contexto da aba necessário para interpretar valores |
| Fluxogramas | 1 descrição gerada = 1 chunk | — | Gerada por modelo multimodal no pré-processamento |

#### 4.2 Por tipo de pergunta do usuário

**Factual pontual** ("Qual é o prazo para X?"): chunks ~300 tokens, retrieval top-3 com threshold mínimo de relevância. A resposta está em um ponto — contexto poluído aumenta risco de confusão.

**Processo/procedimento** ("Como faço Y passo a passo?"): chunks 500 tokens com overlap de 75 tokens, retrieval top-6. Overlap evita quebra de sequência entre chunks adjacentes de um mesmo processo.

**Analítica/comparativa** ("Compare as políticas de A e B"): retrieval top-12 com reranking por cross-encoder (ex: `cross-encoder/ms-marco-MiniLM-L-6-v2`). Aplicar reordenação anti-lost-in-the-middle: chunk de maior score → posição 1; segundo maior → última posição; demais no meio.

#### 4.3 Mitigação do efeito lost in the middle

1. **Reordenação na injeção**: maior score na posição 1, segundo maior na última — LLMs privilegiam extremos
2. **Limite de chunks por tipo de query**: máximo 12 chunks; preferir menos chunks de alta qualidade
3. **Prefixo de metadados padronizado**: `[Fonte: arquivo.pdf | Pág: 12 | Seção: 3.2]` — auditável pelo usuário e informativo para o LLM
4. **Threshold de relevância**: chunks abaixo de cosine similarity 0.70 não entram no contexto, mesmo se o retrieval os retornar

#### 4.4 Avaliação contínua (ausente na v1)

Implementar framework **RAGAS** com amostra de 100–200 pares pergunta/resposta de referência:

| Métrica | O que mede | Target |
|---------|-----------|--------|
| Context Recall | % da informação necessária que foi recuperada | > 0.80 |
| Context Precision | % dos chunks recuperados que são realmente relevantes | > 0.70 |
| Faithfulness | % das afirmações do LLM suportadas pelos chunks | > 0.85 |
| Answer Relevancy | Quão diretamente a resposta endereça a pergunta | > 0.75 |

Rodar avaliação a cada mudança de estratégia de chunking ou atualização de modelo de embedding.

#### 4.5 Controle de acesso e atualização da base

- **Segurança**: metadados de permissão do SharePoint (grupos/usuários autorizados) devem ser indexados junto ao embedding; filtro de acesso aplicado no retrieval antes de retornar chunks ao LLM
- **Atualização incremental**: webhook ou polling no SharePoint/Confluence detecta documentos modificados → re-ingere apenas os documentos alterados → invalida e substitui embeddings antigos no vector store
- **Versionamento de modelo de embedding**: manter hash do modelo de embedding como metadado de cada chunk; ao migrar de modelo, re-embed completo é obrigatório e planejado com antecedência

#### 4.6 Pipeline completo

```
INGESTÃO:
  1. Detecção de tipo e extração estruturada por fonte
     (Document Intelligence / Confluence API / openpyxl + COM fallback)
  2. Limpeza: OCR correction, macro stripping, ciclos de grafo
  3. Chunking semântico por tipo (sentence-transformers para boundaries naturais)
  4. Geração de embeddings + indexação BM25 em paralelo
  5. Armazenamento: vector store (PGVector/Pinecone) + BM25 index (Elasticsearch/BM25s)
  6. Metadados de permissão, fonte, versão e hash do modelo de embedding

QUERY:
  1. Embedding da query + tokenização para BM25
  2. Retrieval paralelo: ANN search (top-20) + BM25 (top-20)
  3. Fusão por Reciprocal Rank Fusion → top-30 candidatos
  4. Filtro de controle de acesso (remove chunks sem permissão para o usuário)
  5. Reranking cross-encoder → top-10
  6. Threshold de relevância: descarta chunks < 0.70
  7. Fallback: se < 3 chunks passam o threshold → resposta de "informação insuficiente"
  8. Reordenação anti-lost-in-the-middle
  9. Montagem do prompt com prefixos de metadados
 10. Geração com GPT-4o
```

### Resumo Executivo (v2)

A base real da NovaTech é ~4,7M tokens (não 4,1M — overhead de Markdown subestimado na v1). **RAG com retrieval seletivo é obrigatório; busca híbrida BM25 + semântica é não-negociável** para cobrir termos corporativos exatos que busca semântica pura não alcança. Os três riscos críticos que a v1 omitiu são: (1) falha silenciosa do `openpyxl data_only=True` em arquivos não-calculados, (2) ausência de fallback quando retrieval não encontra contexto relevante, e (3) exposição de documentos restritos sem controle de acesso no pipeline. Com essas correções, avaliação contínua via RAGAS e pipeline de atualização incremental, o sistema tem base técnica sólida para produção.
