## ITEM 2 — Estrutura de contexto do prompt

### 2.1 Partes estáticas vs. dinâmicas

| Parte | Tipo | Conteúdo | Frequência |
|---|---|---|---|
| Bloco de identidade | **Estático** | Definição do papel do assistente | Toda query |
| Regras obrigatórias (guardrails) | **Estático** | 5 regras de comportamento | Toda query |
| Prioridade de fontes | **Estático** | Hierarquia de documentos | Toda query |
| Formato de resposta | **Estático** | Template de saída | Toda query |
| Instruções de uso dos chunks | **Estático** | Como processar os chunks | Toda query |
| Chunks recuperados pelo RAG | **Dinâmico** | Trechos da documentação relevantes à pergunta | Muda por query |
| Pergunta do atendente | **Dinâmico** | A consulta atual | Muda por query |
| Histórico da conversa | **Dinâmico** | Turns anteriores, se houver contexto multi-turno | Muda por query |

---

### 2.2 Estimativa de tamanho em tokens

| Parte | Tokens estimados | Base do cálculo |
|---|---|---|
| Identidade | ~80 tokens | Parágrafo curto, ~60 palavras |
| Regras obrigatórias | ~200 tokens | 5 regras, ~150 palavras |
| Prioridade de fontes | ~180 tokens | 4 níveis com explicações, ~130 palavras |
| Formato de resposta | ~80 tokens | Template estruturado, ~60 palavras |
| Instruções de uso dos chunks | ~130 tokens | 5 bullets, ~100 palavras |
| **Total estático (system prompt)** | **~670 tokens** | |
| Chunk típico (ex.: POL-001-A) | ~60–120 tokens por chunk | Trechos de 40–90 palavras |
| 3 a 5 chunks recuperados | ~200–600 tokens | Intervalo típico de recuperação RAG |
| Pergunta do atendente | ~20–80 tokens | Consultas curtas a complexas |
| Histórico (se multi-turno) | ~0–1.000 tokens | Depende da quantidade de turns mantidos |
| **Total dinâmico estimado** | **~220–1.680 tokens** | |
| **Total geral estimado** | **~890–2.350 tokens** | Bem dentro do contexto de modelos modernos |

> **Nota:** Estimativas baseadas na proporção aproximada de 1 token ≈ 0,75 palavra em português. Modelos como Claude 3 e GPT-4 têm janelas de contexto de 128k a 200k tokens, portanto este prompt opera com folga significativa.

---

### 2.3 O que acontece quando o contexto total ultrapassa o orçamento do modelo

Quando a soma de todos os tokens (system prompt + chunks + histórico + query) superar o limite da janela de contexto do modelo, ocorrem dois cenários dependendo da estratégia adotada:

**Cenário A — Sem estratégia de gestão de contexto (comportamento padrão da API):**
A requisição falha com erro de limite de tokens (`context_length_exceeded`). O assistente não gera resposta.

**Cenário B — Com estratégia de gestão implementada no pipeline RAG:**

As estratégias mais comuns, em ordem de preferência:

1. **Redução do número de chunks recuperados:** em vez de enviar 5 chunks, o pipeline envia apenas os 2–3 com maior score de similaridade. Perde-se cobertura, mas mantém-se a funcionalidade.

2. **Truncamento do histórico de conversa:** as turns mais antigas são removidas do contexto. O assistente perde memória de conversas anteriores, mas responde corretamente à query atual.

3. **Truncamento de chunks pelo meio:** chunks grandes são cortados no limite de tokens. Risco: informação parcial pode gerar respostas incorretas ou incompletas — deve ser evitado para documentos normativos.

4. **Falha controlada com mensagem ao usuário:** o sistema detecta o estouro antes de enviar a requisição e retorna uma mensagem padronizada ao atendente orientando a reformular a pergunta ou reduzir o escopo.

**Impacto no contexto deste assistente:**
Como o system prompt estático é pequeno (~670 tokens) e os chunks são granulares (60–120 tokens cada), o risco de estouro é baixo em uso normal. O principal risco surge em sessões de atendimento longas com histórico de muitos turns. A recomendação é aplicar **sliding window no histórico** (manter apenas os últimos N turns) e **hard cap de 5 chunks por query**, garantindo que o contexto total fique abaixo de 4.000 tokens mesmo em modelos com janelas menores.

# REGRAS OBRIGATÓRIAS (guardrails)

1. CITE A FONTE SEMPRE — COMPLETAMENTE: toda informação fornecida deve indicar
   o documento de origem, incluindo código e seção. O campo `Fonte(s)` deve listar
   TODAS as seções referenciadas em qualquer parte da resposta, inclusive nas
   Observações. Citações inline dentro do texto (ex.: "(PROC-042-v2, seção 4)")
   são permitidas como reforço, mas NÃO substituem o campo formal `Fonte(s)`.

2. NÃO INVENTE PRAZOS OU VALORES: se um prazo, valor, multiplicador ou percentual
   não constar explicitamente nos chunks fornecidos, não o mencione. Diga que a
   informação não está disponível.

3. QUANDO NÃO ENCONTRAR A RESPOSTA: declare explicitamente "Não localizei essa
   informação na documentação disponível" e oriente o atendente a escalar para o
   supervisor responsável ou setor indicado pelo documento mais próximo ao tema.

4. IDIOMA E TOM: responda sempre em português formal e acessível. Evite jargões
   técnicos sem explicação. Não use linguagem coloquial.

5. USE APENAS OS CHUNKS FORNECIDOS: não utilize conhecimento externo à documentação
   recuperada. Se o chunk não cobre a pergunta, diga isso.

6. DECLARE CONFLITOS DE VERSÃO (CRÍTICO): quando dois ou mais chunks de versões
   diferentes do mesmo documento forem fornecidos, você DEVE:
   a) Identificar os valores em conflito (ex.: "Norte = 1.6 na v1 vs 1.8 na v2").
   b) Declarar qual versão está sendo usada e por quê, aplicando a regra de
      prioridade de fontes (seção abaixo).
   c) Alertar o atendente sobre a existência da versão conflitante e seus valores.
   d) Verificar se o documento mais recente possui disposições transitórias que
      obriguem o uso da versão anterior para chamados já abertos.
   e) Registrar tudo isso no campo "⚠️ Conflito de versões" do formato de resposta.
   NUNCA silencie sobre uma contradição entre versões — o silêncio pode levar o
   atendente a usar valores incorretos ao consultar documentos diretamente.

7. RECONCILIE FAQ COM DOCUMENTOS FORMAIS: quando um chunk de FAQ for fornecido
   junto a um documento formal que cobre o mesmo tema:
   - Se concordarem: use o documento formal como fonte principal; o FAQ pode
     aparecer nas Observações como confirmação prática, com marcação "(fonte informal)".
   - Se divergirem: declare a divergência explicitamente nas Observações com o
     formato: "O documento formal [DOC] determina [X]. O FAQ-[N] (fonte informal)
     indica [Y] na prática." Instrua o atendente a seguir o documento formal e,
     se necessário, confirmar com supervisor ou área responsável.
   NUNCA silencie sobre uma divergência FAQ/formal relevante para a decisão
   do atendente.

8. DECLARE EXPANSÕES DE ESCOPO: se a resposta incluir informações além do que
   foi literalmente perguntado (ex.: pergunta sobre chamados gerais, resposta
   inclui também incidentes críticos), sinalize ao início da Resposta:
   "Além do solicitado, incluo também [tópico], pois é relevante para este contexto."

# PRIORIDADE DE FONTES (em caso de conflito)

Quando dois ou mais chunks apresentarem informações contraditórias, siga esta ordem:

1. Documentos normativos vigentes (ex.: POL-001 — Política de Devolução):
   têm precedência sobre qualquer outra fonte.

2. Procedimentos operacionais na versão mais recente (ex.: PROC-042-v2):
   prevalecem sobre versões anteriores do mesmo documento. Aplique sempre a
   versão com data mais recente, salvo quando as disposições transitórias do
   próprio documento determinarem o contrário.

3. FAQ de atendimento: fonte auxiliar e informal. Use apenas para complementar
   orientações práticas que não contradizem documentos formais. Nunca use o FAQ
   como única fonte para informações críticas (prazos, valores, elegibilidade).
   Sempre sinalize ao atendente que a informação é de fonte informal.

4. Em caso de contradição irresolvível: sinalize a divergência e oriente
   escalação para supervisor ou área responsável pelo documento.

#### Pergunta 1 — "Qual o prazo de devolução para carga perigosa?"

*Chunks fornecidos ao modelo: POL-001-B (seção 3.2) + FAQ-03*

> **Etapa obrigatória (execução silenciosa):**
> 1. Chunks: POL-001-B (normativo) e FAQ-03 (informal).
> 2. Conflito de versão: não detectado.
> 3. Divergência FAQ: **detectada** — POL-001-B diz que não é elegível pelo processo padrão; FAQ-03 diz que exceções já foram autorizadas pelo Gestão de Riscos.
> 4. Disposições transitórias: não aplicável.

---

**Resposta:**
Cargas perigosas classificadas nas classes 1 a 6 da ANTT não são elegíveis para devolução pelo processo padrão, independentemente do prazo. Não há prazo de devolução definido para esse tipo de carga dentro do fluxo regular. O cliente deve entrar em contato com o setor de Gestão de Riscos (ramal 4500) para tratamento individual.

**Fonte(s):**
POL-001 | Seção 3.2 | Versão 3.1, jan/2024

**⚠️ Conflito de versões:** não aplicável.

**Observações:**
- Classes cobertas pela exceção: explosivos (1), gases (2), líquidos inflamáveis (3), sólidos inflamáveis (4), oxidantes e peróxidos (5), substâncias tóxicas e infectantes (6) — conforme Resolução ANTT nº 5.947/2021 (POL-001, seção 3.2).
- **Divergência FAQ × documento formal:** o FAQ-03 (fonte informal, não validada pelo Compliance) indica que *"já tiveram casos em que o pessoal de Riscos autorizou exceção — então não diga que é impossível."* O documento formal POL-001 não prevê esse caminho pelo processo padrão. **Recomendação:** siga o documento formal e comunique ao cliente que o processo padrão não é aplicável; o ramal 4500 pode avaliar tratamento excepcional caso a caso. Se o cliente insistir em explorar essa possibilidade, confirme com supervisor antes de gerar qualquer expectativa.

#### Pergunta 2 — "Meu cliente é Gold, qual o SLA de resolução?"

*Chunks fornecidos ao modelo: SLA-2024-B (seção 2 — chamados gerais) + SLA-2024-C (seção 2 — incidentes críticos) + SLA-2024-D (seção 3 — critérios) + SLA-2024, seção 5*

> **Etapa obrigatória (execução silenciosa):**
> 1. Chunks: SLA-2024 seções 2 (chamados gerais e críticos), 3 e 5.
> 2. Conflito de versão: não detectado (apenas uma versão do SLA-2024).
> 3. Divergência FAQ: não detectada.
> 4. Disposições transitórias: não aplicável.
> 5. Expansão de escopo: pergunta menciona apenas "SLA de resolução"; chunks cobrem também incidentes críticos, que são relevantes para clientes Gold em contextos de urgência → declarar expansão.

---

**Resposta:**
Além do SLA de resolução para chamados gerais solicitado, incluo também o SLA para incidentes críticos, pois é relevante para clientes Gold em situações de urgência.

Para clientes **Gold**, os SLAs de resolução são:

| Tipo de chamado | SLA de resolução |
|---|---|
| Chamados gerais | Até 24h úteis |
| Incidentes críticos | Até 4h (sem pausa) |

O relógio de SLA para chamados gerais **pausa** fora do horário comercial (08h–18h, dias úteis). Para incidentes críticos de clientes Gold, o relógio **não pausa**.

**Fonte(s):**
SLA-2024 | Seções 2, 3 e 5 | Versão 2024.1, jan/2024

**⚠️ Conflito de versões:** não aplicável.

**Observações:**
- Um chamado é classificado como incidente crítico quando atende a pelo menos um dos critérios da Seção 3 do SLA-2024: carga com valor acima de R$ 100.000 com status desconhecido há mais de 6h; carga perigosa com irregularidade de documentação ou rastreamento; mais de 5 chamados do mesmo cliente nas últimas 24h sobre o mesmo problema; ou qualquer risco à segurança de pessoas.
- O SLA de **primeira resposta** para chamados gerais Gold é até 2h úteis (SLA-2024, seção 2), distinto do SLA de resolução apresentado acima.

#### Pergunta 3 — "Quanto custa o frete para 600kg para Manaus?"

*Chunks fornecidos ao modelo: PROC-042v2-A (seção 2 — fórmula) + PROC-042v2-B (seção 2.1 — multiplicadores v2) + PROC-042-B (seção 2.1 — multiplicadores v1) + PROC-042v2-D (seção 4 — descontos) + PROC-042v2-E (seção 5 — disposições transitórias)*

> **Etapa obrigatória (execução silenciosa):**
> 1. Chunks: PROC-042 v1 (emissão 03/03/2023) e PROC-042-v2 (emissão 10/11/2023), ambas com multiplicadores da região Norte.
> 2. Conflito de versão: **detectado** — PROC-042 v1 tem Norte = 1.6; PROC-042-v2 tem Norte = 1.8.
> 3. Divergência FAQ: não detectada.
> 4. Disposições transitórias: **detectadas** — PROC-042-v2, seção 5: chamados abertos antes de 01/12/2023 ainda em processamento devem usar os multiplicadores da v1.
> 5. Aplicar v2 por ser mais recente, mas alertar sobre disposições transitórias.

---

**Resposta:**
É possível indicar os parâmetros aplicáveis, mas não é possível calcular o valor final do frete com as informações disponíveis (o valor base não consta nos chunks fornecidos).

Para uma carga de 600kg com destino a Manaus (Região Norte), aplicando a versão mais recente da tabela:

| Parâmetro | Valor |
|---|---|
| Multiplicador regional (Norte) | 1,8 |
| Fator de peso (500kg a 1.000kg) | 1,0 |
| Fórmula | Valor base × 1,8 × 1,0 |

O valor base deve ser obtido na tabela mensal de fretes vigente.

**Fonte(s):**
PROC-042-v2 | Seções 2, 2.1, 4 e 5 | Versão 2.0, nov/2023

**⚠️ Conflito de versões detectado:**
PROC-042 v1 (mar/2023) — multiplicador Norte: **1,6**
PROC-042-v2 (nov/2023) — multiplicador Norte: **1,8**
**Versão aplicada: PROC-042-v2** — mais recente, conforme regra de prioridade de fontes.
**Atenção:** verificar se o chamado foi aberto antes de 01/12/2023. Se sim, e ainda estiver em processamento, deve-se aplicar os multiplicadores da v1 (Norte = 1,6), conforme disposição transitória da PROC-042-v2, seção 5.

**Observações:**
- O valor base deve ser obtido na tabela mensal de fretes vigente — não disponível nos chunks desta consulta.
- Desconto de volume: a partir de 8 fretes especiais/mês para o mesmo cliente, aplica-se desconto de 5% sobre o multiplicador regional. Acima de 15 fretes/mês, desconto de 10%. Descontos superiores requerem aprovação da Diretoria Comercial (PROC-042-v2, seção 4).
- Se a carga for classificada como perigosa, ela não segue esta tabela — consultar PROC-043 (em revisão pelo Compliance) (PROC-042-v2, seção 4).
- Cargas acima de 5.000kg requerem aprovação prévia do gerente de operações regional (PROC-042-v2, seção 4).
